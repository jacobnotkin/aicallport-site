# AI-ABCX Pricing Architecture

## Purpose

This document defines how AI-ABCX should be priced at launch.

It is not the final public price list.

It is the internal pricing structure that explains:

- what gets priced
- what does not get priced
- how standalone directors should work
- how bundles should work
- how full-system offers should work
- how usage charges should work
- how upgrades should work

This structure should guide:

- recommendation engine output
- guided activation pricing
- partner pricing later
- public pricing communication

---

## Core Pricing Principle

AI-ABCX should not feel like a pile of disconnected software subscriptions.

The customer should understand:

- the system itself gives them corporate structure
- directors are the paid operating functions
- stronger configurations produce stronger outcomes
- they only pay for the functions they activate
- there are no hidden costs

That means pricing should feel:

- modular
- understandable
- transparent
- upgradeable

---

## Structural Rule

## Executives

Executive Officers should be treated as part of the AI-ABCX operating structure, not as separately billed items.

Why:

- executives represent the corporate logic of the system
- customers buy operational functions, not abstract titles
- charging separately for executives would make pricing feel artificial

So:

- executives are included
- directors are what get priced

---

## What Gets Priced

Price the directors.

Each activated director should have:

- a level price
- dependency rules
- where needed, usage pricing

Some directors can be sold alone.
Some only make sense in bundles.
Some should mostly appear inside a broader system recommendation.

---

## What Does Not Get Priced Separately

Do not separately charge for:

- President Dashboard access
- Executive structure layer
- core corporate hierarchy
- internal executive titles
- standard system visibility

These should feel like part of AI-ABCX itself.

---

## Pricing Layers

AI-ABCX pricing should have five layers.

## Layer 1. Standalone Director Pricing

For strong entry directors that can sell independently.

## Layer 2. Bundle Pricing

For combinations that solve one connected business problem.

## Layer 3. Full System Pricing

For broader business transformation setups.

## Layer 4. Usage Pricing

For functions that create variable operating cost.

## Layer 5. Upgrade Pricing

For level changes, added directors, added users, and infrastructure expansion.

---

## Launch Pricing Philosophy

At launch, pricing should optimize for:

- easy first yes
- understandable growth path
- strong upsell logic
- low confusion

Not for:

- extracting maximum price on day one
- complicated enterprise packaging

## Level Pricing Logic

Each director should use A, B, and C pricing logic.

## Level A

Positioning:

- practical entry level
- lighter automation
- lower infrastructure demands
- simpler setup

## Level B

Positioning:

- connected professional operating level
- stronger automation
- more integrated workflow

## Level C

Positioning:

- advanced automation and management depth
- more connected system behavior
- stronger executive visibility and control

Important rule:

The price jump from B to C should often be small enough that good customers feel encouraged to choose C.

That supports upsell and future expansion.

---

## Website Director Pricing Logic

This lane is special because it has two structural cases.

## Case 1. Customer Uses AI-ABCX Website

If AI-ABCX creates and controls the website, price Website Director higher because it includes both management function and website infrastructure value.

Internal launch logic:

- Website A: lower foundational site coordination
- Website B: AI-ABCX website with stronger automation and integration
- Website C: AI-ABCX website with full advanced connection expectations

Current working logic discussed with user:

- Website A with AI-ABCX site: $29/mo
- Website B with AI-ABCX site: $39/mo
- Website C with AI-ABCX site: $49/mo

## Case 2. Customer Uses Existing Website

If customer keeps their own website, Website Director acts as connection, monitoring, routing, and website operations layer.

Current working logic discussed with user:

- Website A with external site: $10/mo
- Website B with external site: $15/mo
- Website C with external site: $20/mo

Important rule:

B and C on external websites should only be approved when the site passes infrastructure requirements.

---

## Call Handling Director Pricing Logic

Call Handling has two price components.

## 1. Director Charge

This is the management function charge.

## 2. Usage Charge

This is the per-minute operating charge.

Reason:

- call handling creates real variable cost
- variable usage should not be hidden inside flat pricing
- transparent usage pricing becomes a competitive advantage

Current working logic discussed with user:

- keep a per-minute price clearly visible
- current starting working reference: $0.15/minute
- later increase may be possible after proof and market adoption

Recommended architecture:

- monthly director fee
- plus minute usage fee

This is cleaner than AI-credit language.

---

## Call Handling Competitive Advantage

The message should be:

- clear dollar pricing
- no confusing credits
- no hidden cost language
- customer sees exactly what usage costs

This is one of the strongest public differentiators versus competitors using AI credit systems.

---

## Estimator Director Pricing Logic

Estimator Director should price as a strong standalone offer because it is one of the most powerful entry paths for service businesses.

Internal pricing logic:

- A should allow strong base estimating
- B should improve workflow depth and connected recommendations
- C should support strongest estimating environment and advanced connected use

Estimator can also become the front door into:

- sales
- follow-up
- call handling
- website

So estimator pricing should stay commercially easy to say yes to.

---

## Scheduling Director Pricing Logic

Scheduling can sell alone.

But B and C should increasingly recommend:

- Dispatch
- Service
- Call Handling

So scheduling pricing should support:

- standalone entry
- stronger operational bundle path

---

## Marketing Director Pricing Logic

Marketing can sell alone, but B and C become much stronger with:

- Website
- Lead Generation
- Follow-Up

So pricing should allow:

- a standalone entry point
- clear upgrade path into a connected growth system

---

## Conditional Directors Pricing Logic

These directors should not be marketed as universal entry products.

Instead:

- price them internally
- show them after qualification
- use them when the business already has enough infrastructure

This keeps public pricing simpler while preserving custom system flexibility.

---

## Bundle Pricing Logic

Bundles should feel more attractive than buying disconnected directors one by one.

Bundle discount principle:

- price should reward valid combinations
- bundle should still protect margin
- discount should feel meaningful enough to encourage broader adoption

Do not create dozens of public bundles.

Use a small set of recurring commercial shapes.

## Full System Pricing Logic

Full-system pricing should always exist.

Reason:

- some businesses want broad transformation
- some companies are unhappy with existing stacked systems
- some will be strong candidates for full C-level configurations

Full system should not mean one generic package.

It should mean:

- a multi-director configuration across the company
- priced from the actual chosen setup

So the public language should be:

- custom full-system pricing
- based on your real business needs

Not:

- one flat public enterprise price

---

## Three Configuration Pricing Model

The guided system should eventually produce three priced configurations.

## 1. Intent Fit

Closest to what the owner says they want right now.

## 2. Improved

Fixes obvious gaps and makes the setup more complete.

## 3. Advanced

Shows the stronger business-growth path.

Each version should display:

- included directors
- levels
- monthly total
- usage assumptions if applicable
- why this setup is recommended

This is the best upsell structure because the customer sees the difference in both capability and outcome.

---

## Usage-Based Pricing Rules

Use usage pricing only where operating costs are truly variable and meaningful.

Likely launch usage-priced lane:

- Call Handling

Possible later usage-priced lanes:

- some messaging-heavy automation
- some data-heavy external services

Avoid turning the whole system into usage chaos.

Most directors should remain monthly priced.

---

## User-Based Pricing Rules

User quantity should affect pricing.

Why:

- larger teams receive more operating value
- more users means broader system access
- bigger organizations should not pay the same as solo operators

Recommended internal rule:

- director pricing stays functional
- user count acts as configuration multiplier or tier factor

This should not feel like classic SaaS seat pricing.

It should feel like:

- business size influences recommended configuration and monthly total

Not:

- every extra person creates annoying microcharges

---

## Upgrade Rules

Customers should be able to:

- add directors later
- upgrade A to B
- upgrade B to C
- expand from partial system to broader system

Upgrade rules should be visible and easy.

Important:

- if a requested upgrade creates a new dependency requirement, the system should explain what else must be upgraded

Example:

- Marketing C may push Website C
- Scheduling B may push Dispatch B in certain operating models

---

## Downgrade Rules

Customers should also be able to remove functions where dependency rules allow.

If removal breaks a valid configuration:

- system should stop the removal
- explain why
- show the lowest valid remaining configuration

---

## Trial Logic

Current agreed direction:

- keep free trial short and serious
- likely guided trial later
- not finalizing implementation now

For pricing architecture, the rule should simply be:

- trial does not replace pricing clarity
- trial is a confidence tool, not the pricing model itself

---

## Partner Pricing Layer

Partner pricing should sit on top of the standard pricing architecture, not replace it.

That means:

- define standard monthly value first
- define partner discount second
- define partner conditions third

This prevents the partner offer from becoming the real default price.

---

## Public Pricing Communication Rules

Public pricing should emphasize:

- modular structure
- custom recommendation
- no hidden costs
- no paying for unused functions
- clear monthly totals
- transparent usage pricing where relevant

Public pricing should avoid:

- AI credit confusion
- overloaded pricing grids
- abstract corporate language without functional meaning

---

## Competitive Positioning Advantage

Against competitors, AI-ABCX pricing can win by being:

- clearer than credit systems
- more custom than fixed bundles
- more honest about dependencies
- more outcome-oriented

The message is:

- your business gets a custom-built operating system
- priced around the functions you actually activate
- with transparent monthly and usage costs

To finalize pricing later, use this order:

1. Lock valid standalone directors
2. Lock valid bundles
3. Lock full-system recommendation logic
4. Lock usage-based lanes
5. Lock level upgrade rules
6. Lock user quantity effect
7. Publish standard pricing
8. Add partner layer

---

## Practical Conclusion

The strongest AI-ABCX pricing model is:

- system structure included
- directors priced
- bundles rewarded
- full-system custom
- usage transparent
- upgrades easy

That keeps pricing clear enough to sell, flexible enough to fit real businesses, and strong enough to support expansion over time.
